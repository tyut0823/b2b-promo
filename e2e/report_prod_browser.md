# b2b-promo 배포된 프론트엔드+백엔드 브라우저 E2E 테스트 리포트

- **대상**: 프론트엔드 `https://b2b-promo-pfey.vercel.app`, 백엔드 `https://b2b-promo.vercel.app` (둘 다 실제 배포)
- **테스트 도구**: Playwright(Python), headless Chromium — `playwright` MCP는 이번에도 연결되어 있지 않아 실제 헤드리스 브라우저로 직접 조작
- **기준 문서**: `docs/4-user-scenario.md` 전체 시나리오(관리자 2.1~2.2, 거래처 담당자 3.1~3.5, 공통 4.1~4.2)
- **실행**: `cd e2e && python run_e2e_prod_browser.py` (`e2e/.env`에 `DATABASE_URL`/`FRONTEND_URL`/`PROD_BASE_URL` 필요, `.env.example` 참고)
- **결과**: 32 / 32 PASS, 스크린샷 32장(`screenshots_prod/`), 원시 결과 `results_prod_browser.json`

## 테스트 중 발견하고 수정한 실제 배포 버그 2건

1. **CORS 차단**: 백엔드 Vercel 프로젝트의 `FRONTEND_ORIGIN` 환경변수가 placeholder(`https://abc-123-fe.vercel.app`)로 남아 있어, 실제 배포된 프론트엔드(`https://b2b-promo-pfey.vercel.app`)의 모든 요청이 CORS로 차단됨. 환경변수를 실제 주소로 수정 후 재배포하여 해결.
2. **프론트엔드가 `localhost:3000`을 호출**: `frontend/src/shared/httpClient.ts`의 `BASE_URL`이 `VITE_API_BASE_URL` 환경변수를 읽지 않고 `'http://localhost:3000'`으로 하드코딩되어 있어서, 배포된 프론트엔드가 브라우저에서 자기 자신의 로컬호스트를 호출하려다 실패(`Failed to fetch`). `import.meta.env.VITE_API_BASE_URL`을 읽도록 수정하고, 빌드 결과물에 실제 백엔드 주소가 박히는지 확인 후 재배포하여 해결. 이 문제는 이전에 미리 지적했었지만 코드 수정이 반영되지 않은 상태였다가 이번 배포 E2E에서 실제로 걸림돌이 되어 확정적으로 고쳐짐.

두 문제 모두 로컬 개발 환경에서는 절대 드러나지 않고 실제 배포 환경에서만 나타나는 종류였다.

## 테스트 스크립트 자체에서 발견한 이슈 1건 (앱 버그 아님)

관리자 샘플 수정 스텝이 두 차례 타임아웃 실패했는데, 원인은 앱이 아니라 테스트 스크립트였다 — 샘플 상세조회 GET 응답이 오기 전에 설명 필드를 채우고 저장 버튼을 클릭해, 폼의 필수 필드(샘플명/시작일/종료일)가 아직 비어 있는 상태로 제출을 시도해 브라우저가 조용히(에러 메시지 없이) 제출을 막았다. GET 응답을 기다린 뒤 입력하도록 스크립트를 수정해 해결. 실제 사용자도 매우 느린 네트워크에서 이론적으로 겪을 수 있는 조건이지만, 이번엔 테스트 자동화의 타이밍 문제였다.
