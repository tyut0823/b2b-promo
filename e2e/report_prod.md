# b2b-promo 운영(배포) 백엔드 E2E 테스트 리포트

- **대상**: 배포된 백엔드 API `https://b2b-promo.vercel.app` (Vercel), DB는 Supabase(`aws-0-ap-northeast-2.pooler.supabase.com`)
- **방식**: 프론트엔드는 아직 배포 확인 대상이 아니라, 브라우저 대신 실제 HTTP 요청(Node `fetch`)으로 API 레벨에서 `docs/4-user-scenario.md`의 시나리오를 직접 검증했다.
- **테스트 데이터**: 실행마다 고유한 임시 ADMIN/BUYER 계정(자가 회원가입이 없는 ADMIN은 Supabase DB에 직접 bcrypt 해시로 생성)과 샘플 3건(진행중/예정/종료)을 만들어 쓰고, **테스트 종료 후 전부 삭제**했다(실행 전/후 `users`/`samples`/`applications` 모두 0건 확인).
- **실행 스크립트**: `e2e/run_e2e_prod_api.js` (`NODE_PATH=<backend>/node_modules node e2e/run_e2e_prod_api.js`로 재실행 가능)
- **결과**: `e2e/results_prod.json`

## 실패 상세: #30 이미지 업로드 (500)

```
POST https://b2b-promo.vercel.app/uploads -> 500 {"message":"서버 오류가 발생했습니다."}
```

**원인**: `backend/src/middlewares/upload.js`가 `multer.diskStorage()`로 `backend/uploads/` 로컬 디스크에 파일을 쓰도록 구현되어 있는데, **Vercel 서버리스 함수는 배포된 코드 디렉터리가 읽기 전용**이라 그 경로에 쓰기 자체가 실패한다(로컬 개발 서버에서는 문제없이 동작했던 이유가 바로 이 차이다). 설령 `/tmp`처럼 쓰기 가능한 경로로 바꿔도, 서버리스 함수는 요청마다 새 컨테이너에서 실행될 수 있어 저장된 파일이 다음 요청/사용자에게 안 보이거나 금방 사라질 수 있다 — 로컬 디스크 저장 방식은 서버리스 배포 환경과 근본적으로 맞지 않는다.

**필요한 조치(범위 밖, 별도 결정 필요)**: 파일을 외부 저장소(예: Supabase Storage, Vercel Blob, S3 등)에 업로드하도록 `upload.js`/`uploads.controller.js`를 바꿔야 한다. 이번 E2E는 검증만 수행했고 코드는 수정하지 않았다 — 저장소를 무엇으로 할지는 사용자 결정이 필요해서 별도로 여쭤보고 진행하는 게 맞다고 판단했다.

## 참고: 로컬 개발과 다르게 동작하는 부분

- 로컬(`npm run dev`)에서는 `backend/tests/uploads.test.js`(5개 테스트)가 모두 통과하지만, 이는 로컬 파일시스템에 쓰기가 가능하기 때문이다. 이번 발견으로 **로컬 테스트 통과 ≠ 운영 배포 환경에서의 동작 보장**이라는 점이 실제로 확인됐다 — 배포 환경(서버리스, 읽기 전용 파일시스템 등)에 의존하는 기능은 운영 대상 자체에 대해 별도로 검증해야 한다.
